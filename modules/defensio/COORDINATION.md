# Defensio — parallel session coordination
Defensio (denial management) is bootstrapped by amendment 36 in one session; parallel feature sessions start at A37. Each session has a TAG (the amendment number it is applying, e.g. A38).

## Reality delta (A36 — overrides any conflicting path in an amendment file)
- Repositories live in `data/repositories/` (the CLAUDE.md rule), never in `modules/defensio/data/`. This file is the source of truth for paths, ownership and published helpers when an amendment says otherwise.
- Denials store: `data/repositories/denials.js` (Defensio-owned, declared in `modules/defensio/module.js`). Appeal-case stub: `data/repositories/appeal-cases.js`. TPA fee stub: `data/repositories/tpa-fee-accruals.js`.
- Defensio screens live under `modules/defensio/features/<feature>/`; a module never imports another module's files (copy Claima's chip helpers, read its repositories).
- `store.batch(fn)` exists — wrap a multi-record seed in it.
- Tier → class canonical map: Hard → Appealable, Soft → Corrigible, Underpayment → Appealable (`TIER_CLASS` in `data/seed/root-causes.js`).

- SHARED files (append-only, one-line edits, never rewrite): modules/defensio/module.js (add your nav entry + routes inside the block marked with your TAG), shared/config.js (add keys under CONFIG.defensio, never edit others'), CLAUDE.md (append your ### entry only), data/store.js (register your entity line only), this file.
- Never edit another session's feature folder or entity files. If you need something changed there, write a request in the Requests section below and stop that part of your work until it is answered.
- data/repositories/denials.js is shared: add helpers in a section headed by your TAG; never modify an existing helper's signature or behaviour.

## Contract (interfaces every session may rely on)
- The denials repository helpers published below, plus everything Claima publishes in modules/claima/COORDINATION.md (claims, remittances, write-offs, coding, charges, batches, lifecycle) and Frontis's pre-auth register (`data/repositories/preauth-requests.js`).
- Cross-feature links go through denial ids, claim numbers, appeal-case ids, accrual ids — never by importing another feature's files. A module never imports another module's files: Claima's chip helpers are copied into modules/defensio/features/denials/denial-chips.js, not imported.
- All dates ISO YYYY-MM-DD; ids not labels; every screen uses ctx.onData; pickers use findActive() helpers.
- Expected amounts are never recomputed here: a denial's evidence reads the claim line's stamped `payerShare` / `allowedExpected` (Claima's assembly stamp) and nothing else.
- Every triage, route, reclassification and resolution is audited under entity `denials`, entityId = the denial id — the same `audit` pattern Claima uses.

## Protocol
1. On start: read this file fully, append "TAG started <time>" under Status.
2. Before editing any SHARED file: re-read it from disk, make the one-line/one-block change under your TAG, save immediately. Never hold a shared file open across other work.
3. When you add a helper others may use: list it under "Published helpers" with its signature and one-line semantics.
4. When you need something from another feature: write it under "Requests" as "TAG → TAG: need <helper/field>, signature <…>"; poll this file every few minutes; the owner answers under the request and implements it in their own files.
5. If you find a conflict, a broken import, or a failing selfCheck caused by another session: write it under "Conflicts" with file + line; do not fix files you don't own.
6. On finish: run node --check on the whole tree and load every Defensio route, then append "TAG done <time>, routes: …" under Status. The last session to finish runs the full-tree check once more.
